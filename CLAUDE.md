# CLAUDE.md

Указания для Claude Code (claude.ai/code) при работе с этим репозиторием.

## О проекте

Эмулятор Бейсика BASIC 02 микроЭВМ «Искра 226» (клон Wang 2200). Должен
одинаково исполнять оба представления программы: плоский текст в КОИ-8 и
«оттранслированный» токенизированный вид.

Стадия: **промежуточного представления больше нет** — интерпретатор
исполняет ту же оттранслированную программу, что лежит в памяти машины
(`docs/DECISIONS.md`, разд. 12); текст транслируется в неё при загрузке.
`STAT04` исполняется из обоих представлений и даёт побайтово одинаковый
экран. Работают `SAVE DC` и `LOAD DC`: программа пишется на диск и грузится
обратно, включая загрузку сегментов с очисткой необщих переменных.
Сделаны числа, строки, массивы, управление, `CONVERT`, `PRINTUSING` с
оператором образа `%`, `READ`/`DATA`/`RESTORE`, **чтение и запись файлов
данных** — и в режиме каталога, и по абсолютным адресам секторов, —
матричные операторы, работа с символьными данными главы 15, операции над
байтами, команды диалога внутри программы, опрос клавиатуры `KEYIN`,
блочный обмен с устройствами, функции пользователя `DEFFN`/`FN`
и **графика** — буфер, растр, преобразования картинки и прямой вывод
`PLOT`.
Есть **окно** — `iskra-win`,
средствами самой системы, без сторонних библиотек; пока только под Windows.
Нет `ASMB` и `$GIO`: они требуют эмуляции процессора.

Формат разобран и проверен на корпусе из 94 файлов.

## С чего начинать любую задачу

1. **`docs/format.md`** — журнал исследования формата. Это главный документ:
   токены, таблицы переменных, грамматика операторов, что доказано и чем, что
   осталось открытым. Содержит и отрицательные результаты — чтобы не повторять
   уже проделанную работу.
2. **`docs/DECISIONS.md`** — проектные решения по эмулятору с обоснованием:
   язык, отказ от Qt и от SDL2, раскладка каталогов, план проверки, риски.
3. **`docs/book/manual-text.txt`** — извлечённый текст руководства 1987 года.
   Там ответы на большинство вопросов по семантике операторов. Искать в нём
   прежде, чем строить гипотезы.

Если задача — «продолжай», смотреть ниже разделы **«Что дальше»**,
**«Допущения, ждущие проверки»** и **«Известные шероховатости»**: там
очередь работ, список неподтверждённых решений и мелочи, до которых руки
не дошли.

## Сборка

Подробности в `BUILD.md`. Коротко:

```
cmake -S . -B build/cmake -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build/cmake
ctest --test-dir build/cmake --output-on-failure
```

Компиляторы на этой машине: `C:/DEV/Qt/Tools/mingw1310_64` (GCC 13.1, для
повседневной работы) и `C:/DEV/Qt/Tools/mingw492_32` (GCC 4.9.2, цель
Windows XP). **Второй цепочкой проверять обязательно** — она и есть причина
запрета на всё новее C++11, и она ловит то, чего не заметит GCC 13.

## Технические решения (кратко; подробности в DECISIONS.md)

- **C++11**, подмножество: без исключений, без `std::regex`, без локалей.
  Тот же стиль, что в `dsk_tools` (он больше не подключён, но повадки
  оттуда).
- **Никакого Qt и никакой SDL2.** Окно делается средствами самой системы:
  под Windows это `user32` и `gdi32`, дальше Xlib, AppKit и канва браузера.
  Экрану 80x24 ускорение не нужно вовсе — кадр перерисовывается только при
  изменении, и блит занимает пару миллисекунд. Всё, что от системы не
  зависит, вынесено в `src/host_common/` (`docs/DECISIONS.md`, разд. 14).
- Цели: Windows XP…11 (MinGW 4.9.2, 32 бита), macOS, Linux, WASM.
- **Сторонних библиотек нет вовсе.** `dsk_tools` был подмодулем и снят:
  образы «Искры» — плоские файлы по 256256 байт, распаковывать нечего, а
  каталог и детокенизацию ядро делает само (`core/catalog.*`,
  `core/detokenize.*`). Держать второй, параллельный путь к диску смысла
  не было: командная строка теперь ходит тем же путём, что и эмулятор.
- Ядро (`src/core/`) не знает ни про SDL, ни про что бы то ни было ещё —
  только про `host.h`.

## Инструментарий исследования

`tools/` — питоновская модель разбора, проверенная на всём корпусе. Пути в
ней вычисляются от корня репозитория, ничего настраивать не надо.

```
py tools/hex2bin.py         # corpus/hex/*_bin.txt → build/corpus/*.bin
py tools/show.py STAT09     # листинг файла из корпуса
py tools/raw.py EDITOR 265  # сырые байты конкретной строки
py tools/verify.py          # построчная сверка всех пар «текст + токены»
py tools/probes/coverage.py # что из языка ещё не исполняется, с цифрами
py tools/probes/bosgi_font.py --check  # сверка шрифта со сканом рис. 3.1
```

Скан знакогенератора (`docs/BOSGI-FONT-fix.jpg`) в git не попадает — он в
`.gitignore` вместе с книгой, — поэтому `bosgi_font.py` из чистой копии не
запустится. Его результат, `src/font/koi7-5x8.txt`, лежит готовым.

`tools/probes/` — одноразовые скрипты, которыми получены отдельные выводы в
`docs/format.md`. Полезны как образцы, но не как библиотека. Исключение —
`coverage.py`: он считает очередь работ по разделу «Что дальше», и цифры
там **надо пересчитывать им**, а не править руками.

Требуется Python 3 (в системе доступен как `py`). Сторонних пакетов не нужно,
кроме `pypdf` для извлечения текста книги и `pillow` для разбора скана
знакогенератора (`tools/probes/bosgi_font.py`).

Наборы про токены содержат **вручную
собранные оттранслированные файлы**: у токенов своя кодировка, и текстовыми
примерами её не проверить. `test_disk` работает на образе в памяти
(`HeadlessHost::mount`) и сверяется с настоящими байтами с дискеты.

**`LOAD DC` транслирует текстовые программы при загрузке.** Младший бит
признака в заголовке файла различает два представления, и на дисках корпуса
текстом лежит половина программ (`М1`, `FAN01`, `STAT01.`, `STAT06`).
Промежуточного вида у машины нет: `ProgramImage::load_text_file()` собирает
листинг из секторов — строки там разделены байтом `85` — и зовёт `tokenize`.
Имена переменных при этом не сохраняются: индексы раздаются по первому
появлению, как у машины, а для `LIST` детокенизатор придумает их заново.

**Текст исполняется только через токены.** Текстовый фронтенд удалён:
`tokenize.*` переводит листинг в образ (`ProgramImage`), а исполняется уже
образ — и снятый с дискеты, и собранный из текста. Единственная точка входа
для текста — `tokenize()` плюс `parse_tokenized_image()`.

Из этого сразу вылезли две дыры в знании формата, которые текстовый фронтенд
прикрывал: **связка `XOR`** и **`SELECT D/G/R`** (единицы измерения углов).
В токенах их байты неизвестны, в корпусе они не встречаются, и транслятор
отказывается их кодировать вместо того, чтобы выдумать байт — выдуманный
уехал бы на дискету через `SAVE DC`. Тесты это фиксируют
(`test_logic`, `test_select`).

Ключевое место — `expr.*`: обе формы сводятся к одному потоку лексем
(`Tok`), и выражение разбирает общий код. Токенизированная форма
двузначна — один байт значит разное в позиции операнда и в позиции
операции, — поэтому `TokenSource::next()` принимает `operand_expected`.
**Заглядывать вперёд можно только в том состоянии, в каком лексема потом
будет прочитана**; иначе двузначный токен разберётся не так. Проверять
конец потока надо у источника (`at_end()`), а не заглядыванием.

**После разбора выражения нельзя читать байты по `src_.pos()`.** Разборщик
уже заглянул вперёд и держит лексему у себя, так что источник стоит за ней.
Запятую и прочие разделители надо забирать через сам разборщик
(`peek`/`consume`), а после `TokenSource::set_pos()` обязательно звать
`ExprParser::reset()` — иначе разбор продолжится с лексемы, прочитанной со
старого места.

**То же и в трансляции: после `Encoder::expr()` нельзя звать
`lex_.take_char(',')` или `take_word("STEP")`** — лексер уже за этой
лексемой. В `tokenize.cpp` для этого есть `StmtEncoder::take_sep()`. Ошибка
не видна на простых операторах и вылезает только на корпусе.

## Вычисление выражений

`src/core/eval.*` — **третий обход той же грамматики**: `ExprParser` строит
дерево, `Encoder` из `tokenize.cpp` выдаёт байты, `Evaluator` — значение.
Дерева он не строит вовсе: «интерпретатор осуществляет пошаговый перевод
операторов» (руководство, разд. 1.2), и выражение перевычисляется при каждом
исполнении, как в машине.

Важное отличие от детокенизатора: **старшинство приходится восстанавливать**.
В потоке лежит плоская инфиксная запись со скобками, а не обратная польская,
поэтому нужен полный рекурсивный спуск: связки → сравнение → сложение →
умножение → унарный минус → степень → операнд.

`src/core/vars.*` — хранилище переменных: числа, числовые массивы,
символьные поля. Вынесено из `interp.cpp`, чтобы вычислитель и исполнение
пользовались одной копией. Индексы элементов туда приходят **уже
вычисленными**: иначе хранилище пришлось бы связывать с разбором.

Исполнение построено на нём же: `interp.cpp` читает операнды из байтов
при каждом исполнении оператора, дерева не строит и позицию хранит парой
«индекс строки, смещение в теле».

**Три ловушки, которые вылезли при переходе** (все — про заглядывание):

1. **Разделитель после выражения читается в позиции операции.** Разбор уже
   заглянул вперёд именно в ней, и попытка заглянуть в позиции операнда
   даёт «смена состояния при заглядывании».
2. **Если разделителя не оказалось, источник надо вернуть** —
   `ExprParser::unpeek()`. Двузначный токен в позиции операнда значит
   другое: `DE` в позиции операции запятая, а в позиции операнда —
   однобайтовый литерал, и он съедает следующий байт.
3. **Индекс переменной в позиции операции — не ошибка, а конец выражения.**
   За выражением может сразу стоять следующий приёмник: разделителей в
   потоке нет. Раньше `ByteSource` считал это ошибкой.

Ещё одно место, где байт двузначен на уровне оператора: **`D6` — это и
`¤` в приставке устройства, и `BEG` у `DSKIP`/`DBACKSPACE`**. У этих двух
глаголов приставка читается без `¤`.

## Печать по образу

`src/core/image.*` — разбор описаний формата и подстановка значений. Общее
место двух операторов: `CONVERT` с образом (разд. 13.6) и `PRINTUSING`
с оператором `%` (гл. 16). Описание формата одно и то же —
`[+|-] ### [.###] [^^^^]`, — но расходятся эти операторы в трёх местах:

- **у `CONVERT` образ целиком одно описание**, а у `%` их сколько угодно, и
  текст между ними «воспроизводится при печати» как есть;
- **незанятые разряды целой части**: `CONVERT` заполняет их нулями
  (`(###)` для 12 даёт `012`), `PRINTUSING` — пробелами. Отсюда флаг
  `pad_zero`;
- **число не влезло**: у `CONVERT` это ошибка, а `PRINTUSING` печатает само
  описание формата — `5555` по образу `###` выдаёт `###` (пример 16.7).

Два правила, о которые легко споткнуться:

1. **Знак принадлежит описанию только вплотную к разрядам.** В образе
   `%U-КРИТ.=-######.####` (`STAT09` 480) первый дефис — часть слова, второй —
   знак числа. Различает их только следующий байт.
2. **Округления нет ни там, ни там**: лишние дробные разряды отбрасываются
   (`140.767685341` по `#####.##` даёт `140.76`), и книга для округления
   прямо велит звать `ROUND(`.

Считается всё **точной десятичной записью**, а не через `double`:
`Number::to_digits()` отдаёт мантиссу и порядок, и подстановка идёт по
цифрам. В машине арифметика двоично-десятичная, и формат печати — последнее
место, где стоило бы это терять.

`PRINTUSING` печатает **не на экран, а на устройство группы `PRINT`**
таблицы устройств: «PRINT — устройство вывода для операторов PRINTUSING,
HEXPRINT и MATPRINT» (разд. 11.5). По умолчанию это адрес `05`, то есть
экран; `SELECT PRINT 0C` уводит вывод на АЦПУ, и так делает `STAT09` 430.
Это единственное место в ядре, которое зовёт `Host::print_char`.

Образ берётся либо из строки с оператором `%` по её номеру, либо прямо из
символьного значения: «формат печати может задаваться также непосредственно
в операторе PRINTUSING в виде символьной константы или символьной
переменной» (разд. 16.2). Различаются они по типу первого операнда.

Разделитель перед элементом решает, что делать, когда описания кончились, а
элементы нет: запятая переводит строку и пускает образ по второму разу,
точка с запятой — только пускает по второму разу (примеры 16.11 и 16.12).
Разделитель в конце оператора решает, переводить ли строку после последнего
элемента (пример 16.13).

## Задание констант: READ, DATA, RESTORE

Указатель начала считывания живёт в `Interp` парой «какой оператор `DATA`,
смещение в его операндах». У машины операторы `DATA` связаны **цепочкой прямо
в потоке**: два последних байта операндов каждого — адрес следующего
(`docs/format.md`, разд. 5, «Хвост оператора DATA»). Восстановить эти адреса
из текста нельзя, их заполняет машина, поэтому `build_data()` строит тот же
порядок просмотром программы. Список строится заново после всякой правки —
`rescan()` зовётся оттуда же, откуда сбрасываются метки `DEFFN'`.

**Значения в `DATA` идут вплотную, без разделителей.** Отсюда главное
правило: берётся ровно **один операнд**, а не выражение. Полный разбор
прочитал бы `E7` следующей константы как `AND` — в позиции операции это она
и есть. Для этого у вычислителя `Evaluator::operand()`, у детокенизатора —
`Decoder::operand()`. На этом же спотыкался `LIST`: `10 DATA 31,334`
выдавал «нет имени для индекса переменной».

**`DE` в начале операндов `RESTORE` читается сырым байтом.** Это запятая
формы `RESTORE ,<строка>` (`VICT` 2190 = `51 03 DE 20 40`), но в позиции
операнда `DE` значит однобайтовый литерал и съедает старший байт номера
строки. После выражения разделитель читается уже в позиции операции, и там
`DE` — запятая как есть.

Отсчёт констант у `RESTORE` **с единицы**: `RESTORE 1,<строка>` встаёт на
первое значение, а не пропускает его. Печатная выдача примера 4.22 в книге
говорит обратное, и спор решён корпусом — разбор в `docs/format.md`, разд. 10,
«Противоречия в самой книге».

Конец данных — **`ERR 27`**, единственный код, прямо названный книгой вне
дисковых (пример 4.21). `ON ERROR` его ловит.

## Файлы данных: запись

Два режима, глава 18 книги целиком.

**Режим каталога.** `DATA SAVE DC OPEN` заводит файл в указателе и открывает
его — заполняет строку таблицы устройств тремя адресами (начальный, конечный,
текущий). `DATA SAVE DC` пишет логическую запись с текущего сектора и двигает
текущий за неё. `DATA SAVE DC END` кладёт концевую запись в текущий сектор и
текущего **не двигает**: она помечает сектор, «откуда можно записывать
данные» (разд. 18.4), и следующая запись ляжет прямо на неё.
`DATA SAVE DC CLOSE` обнуляет три адреса строки, оставляя адрес самого
устройства — его назначает `SELECT`, а не открытие файла.

**`DATA SAVE DC OPEN` пишет в файл ровно одну вещь: `1C 00 01` в последний
сектор.** Счётчик там единица, а не собственная позиция записи, — это
единственное исключение из общего правила (`docs/format.md`, разд. 2,
«Control record»). Доказательство — нетронутый `B0001` на `w001-s2`.

**Режим абсолютной адресации** (разд. 18.9): `BA` — блок в 256 байт из
символьного значения, `DA` — та же логическая запись, но начальный сектор
задан прямо в операторе. Приставка у них общая — `abs_prefix()`: `EB <сектор>
[DE <приёмник>] D0`. Приёмник получает адрес сектора за последним занятым;
у символьного это два первых байта двоичным числом.

**`IF END THEN` — не разновидность `IF`, а отдельный глагол `1E`** с
двухбайтовым BCD номером строки. Признак ставит `DATA LOAD DC`/`DATA LOAD DA`,
прочитав сектор с кодом `1C`: загрузка при этом ничего не делает и текущий
сектор оставляет на концевой записи — на этом стоит пример 18.5 книги.
Обычная запись признак снимает.

**Массив целиком** — и в записи, и в чтении — разворачивается в свои
элементы, «строка за строкой» (разд. 18.3). У числовых массивов это `whole` в
`Evaluator::Target` без места в поле; у символьных место есть, потому что
массив строк — одно непрерывное поле.

## Команды диалога внутри программы

`CLEAR`, `RUN`, `LIST` и `RETURN CLEAR` встречаются не только в диалоге, но и
прямо в тексте программ — и там у них **свои коды**, которых в трансляторе не
было вовсе. Все они выведены из корпуса:

- **`2C CLEAR`**: `14` — это `P`, за ним бывает диапазон строк сырыми парами
  BCD (`DASB2` 790 = `2C 06 14 95 00 DE 99 20`); без операндов — голый
  `CLEAR` (`UDAW` 363); `11` и `12` — `V` и `N`.
- **`2E LIST`**: приставка устройства **только адресом** (`DC DE <адрес>`,
  строки таблицы и дисковода тут ни при чём), дальше один или два номера
  строк через `DE` (`DASB2` 448, `GRAFISN` 1016).
- **`2F RUN`**: пусто либо номер строки парой BCD.
- **`30 RETURN CLEAR`**: пусто либо `CB` — это `ALL`.

**Какой из кодов `11` и `12` это `V`, а какой `N` — корпус не различает.**
Оба встречаются только там, где разницы нет: в `M3`, `M4` и `P3` общих
переменных нет вовсе, а `M0` (единственный с `COM`) чистит прямо перед `END`.
Принято `11` = `V`, `12` = `N` — по единственному мягкому доводу: программа,
объявившая `COM`, скорее пользуется формой, которая общие переменные
**сохраняет**.

Две ловушки исполнения:

1. **`CLEAR P` может стереть строку, из которой его позвали.** Индексы строк
   после правки съезжают, поэтому текущую надо найти заново по номеру, а если
   её больше нет — остановиться.
2. **`RUN` изнутри программы — не рекурсия.** Своего цикла исполнения тут
   заводить нельзя: `RUN` просто передаёт управление, как `GOTO`, а голая
   форма перед этим обнуляет переменные.

`LIST` печатает на устройство группы `LIST`, а не на консольное
(руководство, разд. 11.5), и имена переменных для листинга придумывает
детокенизатор — в потоке их нет вовсе.

## Блочный обмен с устройством

`DATA SAVE BT` и `DATA LOAD BT` (`68` и `66`) шлют и принимают блок байтов
без всякой служебной разметки — в отличие от `DATA SAVE DC`, где у записи
есть заголовки значений. Книга сами операторы не описывает, только называет
`TAPE` их устройством по умолчанию (разд. 11.5); семантика выведена из
корпуса.

**Название группы обманывает: это обмен с любым устройством, а не с лентой.**
Адрес — параметр оператора, и в корпусе их семь разных: экран `05`, АЦПУ
`0C`, графопостроитель `14`, телекоммуникационный интерфейс `34` и `35`
(передатчик и приёмник). Опознаются по таблице ФАУ, приложение 1 книги.

**Адрес после `/` — выражение, а не сырой байт**, и в большинстве случаев
это переменная: программа вычисляет устройство сама (188 операторов из 265).
Разбор — `docs/format.md`, разд. 10.

Отсюда расширение границы с хостом: `Host::device_write()` и
`device_read()`. Их умолчание делает то, что у хоста вообще есть — вывод на
экран и на АЦПУ, — а на всё прочее отвечает `false`, и программа
останавливается. **Молча терять данные нельзя**: обмен выглядел бы
работающим. Устройств ввода, кроме клавиатуры, у хоста нет вовсе, поэтому
`DATA LOAD BT` пока всегда упирается в отказ; свой хост может их добавить,
переопределив эти два метода.

**`KEYIN` — неблокирующий опрос**, а не ожидание: не нажата — исполнение
идёт следующим оператором. Книга оператор не описывает вовсе, семантика
выведена из корпуса (`docs/format.md`, разд. 10). Два номера строк разводят
обычную клавишу и клавишу специальных функций; различить их по коду нельзя,
поэтому у хоста для этого отдельный вопрос — `Host::key_was_special()`.

Отсюда важное для пакетных прогонов: **`--run`, `--run-file` и `--run-text`
ограничены двумя миллионами шагов**. Очередь нажатий там задана заранее и не
пополнится, а цикл `KEYIN A¤,246,246:GOTO 244` без клавиш крутится вечно —
для машины это правильно, а ждать в пакете некому. В окне и в диалоге
ограничения нет.

**`SAVE`/`LOAD` через символьный буфер** (`2A`/`2D` с признаком `DD`) — это
не команда диалога, а способ программы править саму себя. В буфере лежит
**программа в текстовом виде**, строки разделены байтом `85` — тем же, что
разделяет их в текстовом файле на дискете. Разбор с доказательствами —
`docs/format.md`, разд. 10, «Обмен программой через символьный буфер»;
третий номер у `LOAD` это «куда продолжать исполнение».

Из этого следует неприятное: **в буфер попадают придуманные имена**. На
машине там настоящие имена программы, и пользователь `EDITOR` набирает
`C(1)=...`, попадая в свой массив `C`. У нас в листинге стоит `A0(1)`, и
набранное вручную `C(1)` заведёт новую переменную. Внутри эмулятора круг
`SAVE`→правка→`LOAD` сходится (обе стороны пользуются одной таблицей имён),
расходится только внесённое извне.

Обе стороны обмена читают буфер **строго по таблицам**: за именем буфера
сразу идут сырые байты номеров строк, и заглядывание вперёд приняло бы их за
список индексов — та же ловушка 3, что у `BIN(` и байтовых операторов.

## Матричные операторы

**Из всей главы 12 корпус пользуется двумя формами.** Глагол `06 01` даёт
176 операторов, и все они либо `MAT <массив>=ZER` (141), либо
`MAT <массив>=<массив>` (35). Ни `CON`, ни `IDN`, ни арифметики (`+`, `-`,
`*`, `(K)*`), ни `INV`/`TRN` в токенах нет ни разу — их байты не
установлены, и транслятор их кодировать отказывается. Присваивание массива
**переопределяет размерность приёмника** по источнику (разд. 12.2.4).

**`MAT READ` (`06 03`) и `MAT INPUT` (`06 04`) разобраны.** `06 03` во всех
восьми местах корпуса стоит сразу за `RESTORE`, `06 04` — сразу за
приглашением ввода; решает найденная пара `ROM`/`SMAL2`, где строка 26
совпадает вплоть до литералов `DATA` и хвоста `IF … THEN 28`. Скобочная
группа у обоих — **новые размерности**, как у `MAT REDIM`. Оба примера книги
(12.2 и 12.3) воспроизводятся байт в байт; у примера 12.3 при этом повреждена
сканом строка `DATA`, и она восстановлена по печатной выдаче.

**`MAT PRINT` — подкод `06 05`**, единственный, остававшийся без имени: одно
вхождение (`РЕГРЕСС` 3195 = заголовок про матрицу коэффициентов и следом
`<массив>;`). Пример 12.1 книги воспроизводится целиком, включая печать
одномерного массива столбцом и обе разбивки — зонную и плотную.

**Имена графики сверены счётом по парам.** У `EDITOR` (`¤LET` 2 ↔ `06 22` 2,
и обе строки совпадают целиком), у `VICT` и `STAT01` (пять кодов один в
один). Осталось три имени без байтов — `ORIGIN`, `DNPLOT`, `NDRAW`: они есть
только в текстовых листингах, а все подкоды `06 xx`, встречающиеся в корпусе,
уже названы. Выдумывать их нельзя (`docs/format.md`, разд. 5).

**`REPLACE` и `$TRAN(` — оттуда же, из главы 15.3.** `REPLACE` заменяет
цепочки символов и считает замены; **концевые пробелы поля в замене не
участвуют**, иначе пример 15.6 (`REPLACE K,E¤(),HEX(2020),HEX(20)` в цикле,
пока `K<>0`) не сошёлся бы никогда — хвост поля давал бы пары пробелов без
конца. Подставленное заново не просматривается: разбор идёт дальше за
подстановкой.

`$TRAN(` перекодирует всё поле: без `R` — по таблице, где код байта это
номер в ней, считая с единицы; с `R` — по списку пар «на что, что»,
кончающемуся парой пробелов. В потоке `R` это хвост `DE 00` после
закрывающей скобки (`EDITOR` 290 против 4760). **Маску `hh` книга описывает,
а в корпусе её нет**, и как она кодируется — неизвестно; транслятор её тоже
не берёт.

**`MAT COPY` и `MAT SEARCH` — не из главы 12, а из главы 15**: это операторы
над символьными переменными, и к матрицам они отношения не имеют. `MAT COPY`
переписывает байты, игнорируя границы элементов массива; знак минус слева
значит «читать с последнего байта», справа — «писать с последнего». Вход и
выход бывают одной переменной (подпрограмма вставки из примера 15.5), поэтому
байты источника снимаются в буфер до записи.

`MAT SEARCH` возвращает **список позиций** двухбайтовыми числами, нумерация
с единицы; если список не заполнился до конца, за последним номером идут два
нуля. Хвостовые пробелы искомого значения в сравнение не входят — их
отрезают, а чтобы они считались, книга велит задавать значение через `STR(`.
Знаки `*` (по маске), `%` (с отождествлением) и `#` (диапазон) книга
описывает, но их байты в корпусе не встречаются, и разбор на них
останавливается.

## Операции над байтами

Вся глава 14 книги, кроме упаковки чисел. Устроено это проще, чем кажется:
**`AND`, `OR` и `XOR` — частные случаи `BOOL`**, книга так и говорит
(«операторы BOOL 8 и AND, BOOL Е и OR, BOOL 6 и XOR эквивалентны»). Разряд
результата — это разряд кода операции под номером «аргумент1 × 2 +
аргумент2», и вся четвёрка операторов сводится к одной функции в четыре
строки.

**Разделителя между аргументами в потоке нет вовсе.** `DE hh` — это не
запятая с кодом, а однобайтовый литерал: `AND(B¤,DF)` = `43 03 23 DE DF`,
а `AND(A¤,B¤)` = `43 02 1E 15`, два индекса подряд. Поэтому второй аргумент
читается как **один операнд** (`Evaluator::operand()`, тот же, что у `DATA`),
и обе формы разбираются одним кодом.

Отсюда же ловушка: **приёмник надо индексировать строго по таблицам**. За ним
сразу стоит второй аргумент, и заглядывание вперёд принимает его индекс за
список индексов приёмника — ровно тот случай, что у `BIN(` и `INIT` (ловушка
3 выше). `AND`, `OR`, `XOR`, `BOOL` и `ADD` пополнили этот список.

`ADD` и `BOOL` пришлось добавить и в транслятор, и в детокенизатор — их там
не было вовсе.

**Загрузка сегментов сделана целиком.** `LOAD DC` и `LOAD DA` (глагол `72`,
разобран по паре `LL`/`L2` и книге, разд. 19.1) делят общий хвост из трёх
номеров строк: «стирается программный текст, начиная со строки… стираются все
необщие переменные… программа будет выполняться, начиная со строки». В потоке
номера идут сырыми парами BCD, и **пропущенный виден двумя `DE` подряд**
(`LL` 51 = `1000,,53`). Строки вне стёртого диапазона остаются, одинаковые
номера замещаются сегментом. **`SAVE DA` книга описывает, но в корпусе его
нет, и байт неизвестен** — транслятор отказывается его кодировать.

**`COM CLEAR` — не форма `COM`, а свой глагол `37`** (разбор —
`docs/format.md`, разд. 5). Он двигает границу общих переменных, а переменных
не стирает: «оператор COM CLEAR не стирает переменные из памяти»
(руководство, разд. 19.3). Операнд необязателен, и оба случая книги — одно
правило: **граница встаёт на названную переменную**, без операнда — в начало
области. У нас это `VarStore::set_common_boundary`, и видно её действие по
тому, что после неё стирает `CLEAR N`.

**`ADD C` — не признак у `ADD`, а свой глагол `63`.** Раньше признак
кодировался выдуманным байтом `D4` по аналогии с `ROTATE C`; это оказалось
неверно. Разобрано на паре `SLIDE`/`SL2` (`SLIDE` 1430 против `SL2..` 1500 —
оператор в оператор) и подтверждено тем, что **ни один** из 29 операторов
`4A` в корпусе не начинается с `D4`. Глагол `63` был самым частым из
неопознанных: 87 операторов в 20 файлах. Разбор — `docs/format.md`, разд. 5,
«Глагол `63` — это `ADD C`». В тексте пишут двояко — `ADDC(` (книга) и
`ADD C (` (`SLIDE`, `SIG`, `ROM`); транслятор берёт оба, обратно выдаёт
`ADD C(`.

**`PACK(`/`UNPACK(`** — десятично-упакованный формат, разд. 13.7. Цифровая
часть **подтверждена живыми данными**: файлы `TEST`, `FF` и `CHROM1` на
образах `w009` записаны программой `GC121` по образу `####` и дают по
20 000 байт чистого BCD, две цифры на байт. Размер группы —
«тетрад = знак + число `#`, округлить вверх, плюс байт порядка при `^^^^`» —
сходится пятью независимыми способами. Тетрада знака и байт порядка в
корпусе не встречаются ни разу и взяты по домашним правилам формата; разбор
целиком — `docs/format.md`, разд. 10.

`HEXPRINT` (глагол `50`) сделан заодно — иначе примеры глав 13.5 и 15 не
проверить. Список у него тот же, что у `PRINT` (`DE` запятая, `DD` точка
с запятой, 64 вхождения в корпусе), но **запятая переводит строку**, а не
двигает по зонам, и печатает он на устройство группы `PRINT`, как
`PRINTUSING`.

## Обратная трансляция «токены → текст»

`src/core/detokenize.*` — это `LIST` диалогового режима и вторая половина
круговой проверки: `tests/test_detokenize.cpp` гоняет корпус через
«токены → текст → токены» и требует тех же байтов. Так проверяется обход
операторов **без всякой семантики** — на нём потом будет стоять интерпретатор.

На сегодня из 1808 сравнимых строк сходится **1772**, ещё 33 расходятся только
рабочими полями — итого 1805 из 1808. Детокенизируется 1808 строк из 1838.
Глаголы разобраны все, что встречаются в парах; остаток — длинный хвост, и
больше половины его приходится на одну открытую задачу (ниже).

По всему корпусу (не только по парам) не детокенизируется 569 строк — это
считается так:

```
for f in corpus/bin/* build/corpus/*.bin; do
    ./build/cmake/iskra.exe --detok "$f" | grep -c " ??? "
done | paste -sd+ | bc
```

**Имена переменных приходится придумывать**: в потоке их нет вовсе, есть
индексы. Поэтому `detokenize()` заполняет `NameTable` (индекс → имя вида
`A`, `A0`…`A9`, `B`…), и **та же таблица нужна обратной трансляции** —
иначе `tokenize()` раздаст индексы заново, по первому появлению в тексте.

**Главное, что мешает добить остаток** — открытый вопрос формата: у
символьной переменной «скаляр или массив» по таблицам не различается,
`build_vars` угадывает «массив» (docs/format.md, разд. 6). Если программа
пользуется такой переменной без индекса, детокенизатор либо принимает
следующие байты за список индексов, либо заводит для неё новую запись при
обратной трансляции. Отсюда 24 неразобранные строки и три расхождения в
`STAT03`. Частично спасает правило «если сразу за приёмником стоит `=`,
списка индексов там нет» — оно чинит присваивания, но не списки приёмников.

**Три ловушки, одинаковые в обе стороны** — их же список в CLAUDE.md выше:
первый аргумент `STR(` индексируется только по таблицам; приёмники `BIN(`,
`INIT`, `KEYIN` — тоже; и **конец операндов надо спрашивать у разборщика, а
не у источника** — заглянутая лексема уже прочитана из источника, и
`at_end()` соврёт.

## Трансляция «текст → токены»

`src/core/tokenize.*` переводит текстовый листинг в тот же вид, что лежит в
памяти машины (`docs/DECISIONS.md`, разд. 12). Проверяется построчной сверкой
с парными оттранслированными файлами — `tests/test_tokenize.cpp`, там же
гистограмма причин отказа, она и есть очередь работ.

На сегодня сходится **1803 из 1837** сравнимых строк, ещё 33 расходятся
только рабочими полями — адресом возврата `DEFFN'` и цепочкой `DATA`, которые
машина заполняет при исполнении и восстановить их из текста нельзя. Итого
1836 из 1837. Целиком транслируются `STAT04`, `STAT02`, `STAT08`, `STAT09`.
**По существу расходится одна строка** — `STAT03` 20, где `MAT REDIM`
переписал индексы в `DIM` (`docs/format.md`, разд. 6).

Не транслируется тоже одна строка — `EDITOR` 82, и виновата не трансляция:
в текстовом листинге внутри `HEX(` лежат двоичные байты, дамп их не сохранил.

**Дальше двигать эту цифру некуда — корпус пар исчерпан.** Следующая проверка
трансляции возможна только на новых парах «текст + токены».

**Три правила, на которых всё держится** (`docs/format.md`, разд. 6):

1. Индексы раздаются по первому появлению имени, поэтому **одно лишнее или
   пропущенное имя ломает всю программу дальше**. Отсюда следующие два.
2. Ключ переменной — имя **вместе с признаком массива**: `B¤` и `B¤()` —
   разные переменные с разными индексами. `MAT Q=ZER` при этом называет
   массив без скобок, для этого у лексера есть `expect_array()`.
3. Неразобранная строка **откатывает таблицу имён** (`NameTable::truncate`):
   иначе `SAVE DC R¤T(…)` завёл бы переменные `S` и `A`, которых в машине нет.

Что реализовано из языка: `PRINT` (`AT(`, `TAB(`, `HEX(`, зоны,
разделители), `INPUT`, присваивание в несколько целей, `DIM`/`COM` и
массивы до двух измерений, `FOR`/`NEXT`, `IF`/`THEN`, `GOTO`,
`GOSUB`/`RETURN`, `ON … GOTO/GOSUB`, `GOSUB'`/`DEFFN'`, `STOP`, `END`, `REM`,
`SELECT`, функции `SQR`/`ABS`/`INT`/`SGN`/`LOG`/`EXP`, `#PI`.

Связки условий `AND`, `OR`, `XOR`. **Старшинства у них нет: все три
равноправны и вычисляются слева направо** (руководство, разд. 4.5), то есть
`A OR B AND C` значит `(A OR B) AND C`. `XOR` в токенах не поддержан — в
корпусе он ни разу не встречается связкой, и байт неизвестен.

Символьные данные: переменная — поле байт постоянной длины (16 по
умолчанию, `DIM` задаёт 1…253), массив строк — одно непрерывное поле,
`STR(` работает и слева от знака равенства, есть `LEN`, `NUM`, `VAL`, `POS`.
`BIN(` — обратное `VAL(` преобразование: `BIN(<приёмник>[,2])=<а.в.>`
записывает целую часть значения в один или два двоичных байта. `INIT(<код>)`
заполняет все байты перечисленных приёмников одним значением.

`CONVERT` в обе стороны с образами, `LINPUT`, `MAT REDIM`. Двухбайтовые
глаголы `06 <подкод> <len>` разбираются структурно все — на нереализованном
подкоде разбор останавливается точно, без рассинхронизации.

**`PRINT /<адрес>` уводит вывод оператора на устройство.** Приставка та же,
что у блочного обмена (`PRINT /10,HEX(0D)` = `4C 07 DC DE 10 DE …`,
`VICT` 80), и в корпусе таких операторов 182 в 33 файлах, из них 115 — экран.
Адрес `05` идёт обычным путём, со знакоместами и курсором; прочие получают
байты через `Host::device_write`, и если устройства у хоста нет, программа
останавливается. **Зоны, `AT(` и `TAB(` при выводе на устройство — отказ**:
это операции над курсором экрана, а в корпусе с не-экранным адресом они
встречаются два раза на всё.

**Графическое устройство `/10` подпадает под ключ `-i`.** Оно принимает
управляющие коды, которых мы не разобрали: на весь корпус их пять — `0D`,
`0E`, `0F`, `01` и пара `01 02`. Взять их неоткуда (см. ниже), поэтому без
ключа программа останавливается, а с ключом вывод на `/10` пропускается —
как `ASMB` и `$GIO`. Прочие неизвестные адреса ключ **не** покрывает: там
устройства у хоста просто нет, а это другое. Ровно из-за этого `VICT` вставал
на строке 80 (`PRINT /10,HEX(0D)`), а теперь идёт дальше.

Помеченные подпрограммы: `DEFFN'` с формальными параметрами (числовыми и
символьными), `GOSUB'` с выражениями, несколько входов в одну подпрограмму,
`DEFFN'` с текстом клавиши спецфункции (разбирается, но клавиш ещё нет).
Разд. 10.4 книги и разд. «Помеченные подпрограммы» `docs/format.md`.

Функции пользователя: `DEFFN <имя>(<формальная переменная>)=<а.в.>` и
обращение `FN<имя>(<а.в.>)` (разд. 4.8). **Имя функции — не переменная**:
это латинская буква либо цифра, пространства имён разные, и `DEFFN A(H)`
уживается с переменной `A` (пример 4.20). В потоке — глагол `5A` и токен
`F0`, оба разобраны в этом заходе (`docs/format.md`, разд. 5, «Функции
пользователя»). Определение ищется просмотром всего текста программы, как
и `DEFFN'`: «функция может быть объявлена в любом месте программы,
независимо от того, где она будет использоваться». Функция может звать
другую функцию (`GC121` 2310), поэтому глубина вложенности ограничена —
`FN Q(X)=FN Q(X)` иначе обвалило бы стек молча.

Дисковое чтение: `DATA LOAD DC OPEN`, `DATA LOAD DC`, `DSKIP`,
`DBACKSPACE`, `LIMITS`, `LIST DC`, `SCRATCH`, `SCRATCH DISK` в обеих формах.

`LIST DC` — выдача указателя каталога по разд. 5.1 книги: тип диска
(`FIXED`/`REMOVABLE`), `INDEX SECTORS`, `END CAT.AREA`, `CURRENT END`, дальше
таблица `NAME/TYPE/START/END/USED` с типами `P`, `D`, `SP`, `SD`. Графа
«Использовано» берётся из концевой записи файла, а не из указателя.
**Ширины столбцов восстановлены, а не прочитаны**: в скане книги три примера
`LIST DC`, и разбивка пробелами в каждом своя — распознавание её потеряло.

`ON ERROR` во всех трёх формах
(`GOTO`, `THEN`, `GOSUB`) и с отменой. Слои снизу вверх — `number.*`
(8-байтовое число), `disk_record.*` (записи), `catalog.*` (указатель и хеш
имени), `devtable.*` (строки `#0`…`#7`), операторы в `interp.cpp`.
«Дескриптор файла» — строка таблицы устройств, её выбирает программа
оператором `SELECT #n`, а не выдаёт система.

`SELECT` меняет таблицу устройств (`src/core/devtable.*`): именованные
группы, строки `#0`…`#7`, пауза `P`, единицы измерения углов. Коды групп
`07` PRINT, `0A` DISK, `05` P и `00` `#n` подтверждены парами «текст +
токены», остальные опознаны косвенно; код `01` не опознан и при исполнении
даёт ошибку, а не догадку.

**Опись того, что ещё без кода** — `docs/format.md`, разд. 5, «Опись: что ещё
не имеет кода». Коротко: шесть тригонометрических функций (`F9` вероятно
`SIN(`, `FD` вероятно `ARCTAN(`), связка `XOR`, пять названий групп `SELECT`
и единицы углов `D`/`G`/`R`, `SAVE DA`, отрицательный порядок константы,
матричная арифметика с `CON`/`IDN`/`INV`/`TRN`, маска `hh` у `$TRAN(`,
признаки `MAT SEARCH`, формы `LIST V`/`*`/`¤`/`%`, `ORIGIN`, `DNPLOT`,
`NDRAW` и форма `INPUT ¤<переменная>`.

**Тригонометрия распознаётся, но не кодируется.** `SIN(`, `COS(`, `TAN(`,
`ARCSIN(`, `ARCCOS(`, `ARCTAN(` в таблице ключевых слов есть, а байтов у них
нет: свободны `F9`–`FC`, и какое имя за каким — корпус не показывает. Слова
всё равно должны быть в таблице: без них `COS(X)` разбирается как переменная
`C` и хвост `OS(X)`, то есть **молча неправильно**. Честный отказ лучше.

**Транслятор покрывает почти весь язык корпуса** — список глаголов и их
операндов в `docs/format.md`, разд. 5, «Грамматика операндов». Сверх
перечисленного выше разбираются: `PRINTUSING`, `READ`/`RESTORE`/`DATA`,
`RUN`, `RETURN CLEAR`, `KEYIN`, `PACK(`/`UNPACK(`, `ROTATE`, `BIN(`,
`AND(`/`OR(`/`XOR(`, `MAT` (`=ZER`, `REDIM`, `COPY`, `SEARCH`), `LINPUT`,
`REPLACE`, `SCRATCH`, `SCRATCH DISK`, `LIMITS`, `DSKIP`/`DBACKSPACE`,
`VERIFY`, `COPY`, `SAVE DC`, `DATA LOAD/SAVE BT/BA/DA`, `$GIO`, `$TRAN(`, `$OPEN`,
`$LET`, `$COPY`, `ASMB`, графика `NPLOT`/`DRAW`/`STRETCH`/`LABEL`, функции
`ROUND(` и `RND(`.

К ним добавились `SAVE`/`LOAD` через символьный буфер, `LIST DC`,
`LOAD DC`, `WINDOW`, а также `DEFFN` и обращение `FN<имя>(`.

**Исполняется теперь всё, что транслируется**, кроме двух
машинозависимых глаголов (`ASMB`, `$GIO`) и одного неопознанного (`33`).
Разбор оператора в байты и его исполнение — разные вещи, но разрыва
между ними больше нет.

**Ключ `-i` покрывает три вещи**, а не две: `ASMB`, `$GIO` и вывод на
графическое устройство `/10`. Общее у них одно — здесь этого нет и не будет,
а молчаливый пропуск сделал бы прогон неправдоподобным незаметно для
человека.

**Машинозависимые операторы — третий случай, помимо этих двух.** `ASMB`
(`06 25`) и `$GIO` (`40`) требуют эмуляции машины на уровне процессора и
аппаратуры; здесь их не будет (`docs/DECISIONS.md`, разд. 1). Ключ **`-i`**
у обоих хостов велит такие пропускать, а **по умолчанию программа
останавливается** — молчаливый пропуск сделал бы прогон неправдоподобным
незаметно для человека. Список глаголов один на всё —
`Interp::machine_verb()`; графика в него не входит, там нужен второй растр,
а не процессор.

**Математические ошибки — ошибки машины.** Деление на ноль, переполнение,
корень из отрицательного, логарифм неположительного и отказ возведения в
степень получают код `03`, и `ON ERROR` их ловит: «если ошибка математическая,
то выполняется оператор возврата `RETURN`, при этом оператор, на котором
произошла ошибка, пропускается» (руководство, пример 11.11). Вычислитель про
`ON ERROR` не знает и только помечает причину (`Evaluator::math_fail`), а
превращает её в ошибку машины `Interp::exec`.

**Ошибки машины и ограничения эмулятора — разные вещи.** `ON ERROR` ловит
первые (`Interp::machine_error`, код из `core/errors.h`) и не ловит вторые
(`Interp::fail`). Иначе нереализованный оператор молча превратился бы в
«сбой ввода-вывода», и дыра в эмуляторе выглядела бы как поведение машины.

**Три ловушки кодировки, о которые легко споткнуться снова.**

1. Первая запятая `STR(` в потоке не кодируется — после первого аргумента
   надо заглядывать в состоянии «ожидается операнд».
2. По той же причине **первый аргумент `STR(` не индексируется по
   заглядыванию**: `STR(Z¤,67)` иначе читается как `Z¤(67)`. Там работает
   только признак массива из таблиц — в `Tok` для этого отдельное поле
   `table_array`.
3. **Приёмники `BIN(` и `INIT` — тоже.** У `BIN(` за приёмником сразу идёт
   значение (`BIN(A¤)=J%` = `4B 02 22 3B`), у `INIT` запятых между
   приёмниками нет вовсе (`INIT(00)A¤,O¤`). Все три места вызывают
   `parse_lvalue(target, true)`.

Во всех прочих местах индексация символьной переменной определяется по
тому, начинает ли следующий байт операнд (разд. 7).

**Размеры массивов в оттранслированной форме есть только в таблицах
переменных**: оператор `DIM` там несёт одни индексы. Читает их
`build_vars()` в `program.cpp` по разд. 6 `docs/format.md`. Осторожно с
`MAT REDIM`: выросший массив получает новый индекс, и в `DIM` стоят
«теневые» индексы с размерами уже после переопределения.

**«Строка-скаляр или массив строк» решается только по адресам**: у скаляра
поле «число элементов» числом элементов не является вовсе (у `A¤` в `EDITOR`
там 129 при длине 1). `build_vars()` идёт по лестнице правил из разд. 6
`docs/format.md`: чётный размерный код, вторая размерность, затем точные
равенства с разностью адресов соседних записей таблицы 1. Когда адресов нет
(невыполнявшиеся файлы, `STAT05`), остаётся догадка по числу элементов, и она
ошибается в сторону «массив».

## Диалоговый режим

`src/core/console.*` — то, что видит человек за машиной: приглашение `:`,
построчный ввод, правка текста программы, `RUN`, `RUN <n>`, `LIST` со всеми
формами диапазона и параметром `S`, `CLEAR`, `CLEAR P`, `CLEAR V`, `CLEAR N`,
исполнение строки без номера в режиме непосредственного счёта. Заставка —
`READY BASIC 02 05.10.84`, как в разд. 3.2 книги.

`Console` не знает ни про терминал, ни про окно: он работает с `Host` и
`Screen`. Кто ждёт нажатия — решает хост: `Host::wait_key()` по умолчанию
крутит `poll_key`/`present`, а `HeadlessHost` сводит его к `poll_key` —
пустая очередь у него значит «сценарий кончился», а не «пока не нажали».

**`LOAD DC` в диалоге и в программе ведёт себя по-разному:** «в режиме
непосредственного счёта оператор `LOAD DC` (`LOAD DA`) только загружает
программу в оперативную память без её предварительной очистки» (разд. 19.1)
— ни `CLEAR N`, ни запуска. Переменные достаются новой программе чужими:
индексы-то позиционные. Потому книга и советует набирать `CLEAR` перед
загрузкой.

Имена переменных после `LOAD DC` раздаются заново (`Console::refresh_names`):
в потоке имён нет вовсе, а индексы стали от другой программы. Признак
подмены — рассогласование числа имён с числом переменных образа.

Проверяется сеансами по сценарию (`tests/test_console.cpp`): нажатия
подаются очередью, экран сверяется целиком, побайтово.

Настоящий экран — `iskra-win [ОБРАЗ]` (разд. «Окно» ниже). В терминале то же
самое доступно как `iskra --console [ОБРАЗ]`: хост `TermHost` в `main.cpp`
повторяет экран построчно, читая строки со стандартного ввода. Это подпорка
для сборок без окна и для конвейеров, а не второй способ работы.

## Окно

`src/host_win32/` — окно средствами самой системы: `user32` и `gdi32`, и
больше ничего. Готовый `iskra-win.exe` тянет только `KERNEL32`, `USER32`,
`GDI32`, `SHELL32` и `msvcrt`; доставлять с ним нечего. Обоснование выбора,
раскладка по системам и цена — `docs/DECISIONS.md`, разд. 14.

```
iskra-win [ОБРАЗ] [--dN ОБРАЗ] [--rN] [--text ЛИСТИНГ] [--scale N] [-i]
iskra --console [ОБРАЗ] [--dN ОБРАЗ] [--rN] [-i]        то же в терминале
```

**Образы подключаются ключами `--d0`…`--d3`**, по дисководу на ключ; номера
те же, что в `SELECT`: `0` — `18F`, `1` — `18R`, `2` — `1CF`, `3` — `1CR`
(`DeviceTable::drive_index`). Образ без ключа идёт в нулевой. `--r0`…`--r3`
запрещают запись на свой дисковод — это заклеенная прорезь, а не свойство
машины: `Host::disk_write` возвращает `false`, и программа видит отказ
записи. Кода ошибки у него нет (см. `core/errors.h`), поэтому `ON ERROR`
получает `??`, а не выдуманный номер. Разбор ключей общий —
`host_common/disk_args.*`.

**Запись идёт прямо в файл образа** — и в окне, и в терминале. Автотесты при
этом работают на образе в памяти (`HeadlessHost::mount`): прогон обязан быть
воспроизводимым и ничего на диске не трогать. По той же причине `--list`,
`--cat`, `--run` образ по-прежнему только читают.

Разделение труда такое: `src/host_common/renderer.*` превращает знакоместа
в точки и про систему не знает вовсе (потому и проверяется `test_render`
без всякого окна), а хост заводит окно, разбирает события и выкладывает
готовый кадр. На каждую следующую систему приходится только вторая часть.

Что стоит знать про хост на Win32:

- **Кадр — растр трубки, 560x256.** Знакоместо 7x10 при 80x24 даёт 560x240,
  то есть текстовый блок занимает кадр по ширине целиком, а сверху и снизу
  остаются поля по 8 точек. Они часть растра, а не пустота за краем кадра, и
  растеризатор их закрашивает.
- **Точка квадратная**: `DOT_TALL` = 1, никаких сжатий. Прежде здесь стояла
  двойка — она подгоняла кадр 640x240 под 4:3.
- **Увеличение подбирается под экран.** `--scale N` задаёт целый множитель
  кадра; без ключа берётся наибольший, при котором окно влезает в рабочую
  область (`SPI_GETWORKAREA`). Иначе окно с зашитым умолчанием открывалось
  бы за краем у всякого, чей монитор меньше.
- Растеризатор меряет кадр знакоместами, а не глифами: межбуквенный просвет
  живёт в поле, и выделение переставляет знакоместо целиком вместе с полями.
- **Кадр рисуется только при изменении.** `Screen::dirty()` для этого и
  заведён; вдобавок кадр перерисовывается по миганию курсора, раз в
  полсекунды. Ускорение экрану 80x24 не нужно.
- **Показывает исполнитель, по ходу программы.** `Interp::loop()` зовёт
  `Host::present()` на каждом операторе, которому есть что показать
  (`Screen::dirty()` либо `Raster::dirty()`), и раз в 256 операторов просто
  так — иначе окно не разбирает события. Закрытое окно останавливает
  программу. Без этого рисующая в цикле программа показывала бы один
  последний кадр, а печатающая — ничего до самого конца
  (`docs/DECISIONS.md`, разд. 14).
- **Скорости у эмулятора нет**: около пяти миллионов операторов в секунду,
  на три порядка быстрее машины. Задержки, написанные пустым циклом `FOR`,
  пролетают незаметно; замедления мы не делаем — выверить его нечем.
- **Увеличение только целое**, `StretchDIBits` с `COLORONCOLOR` — ближайший
  сосед, без сглаживания. Что не поместилось в окно, становится полями и
  закрашивается чёрным; `WM_ERASEBKGND` возвращает 1, иначе система мигала
  бы белым.
- **`--text ЛИСТИНГ` кладёт текстовую программу в память** до приглашения —
  как если бы её набрали с клавиатуры. Дальше `RUN`. Это единственный способ
  прогнать в окне программу, которой нет на дискете: файлового диалога у нас
  нет, а графику иначе не посмотреть — растр показывает только окно.
- **Лист графопостроителя — второе окно**, и заводится оно лениво, по первому
  `¤COPY /14` (`docs/DECISIONS.md`, разд. 15). Закрыть его можно, эмулятор не
  остановится: это бумага, а не машина, и следующий вывод откроет её заново.
  Класс окна тот же, что у экрана, сообщения разводятся по `HWND`. Цвета у
  листа свои — тёмное перо на светлой бумаге, `Renderer::set_paper_colors`.
- **Графика ложится на знакоместа исключающим или** (`OVERLAY_XOR`): линия
  видна и на пустом поле, и поверх знака. Как смешивает два своих устройства
  сама трубка, книга не говорит вовсе; сложение под рукой —
  `set_overlay(OVERLAY_OR)`.
- **Клавиши берутся из `WM_CHAR`**, а не по положению: окно широкое, и
  кириллица приходит с любой раскладки. Перевод в КОИ-8 — общий
  `unicode_to_koi8()` из `core/koi8.*`. Клавиш специальных функций пока нет
  (`DEFFN'` их разбирает, нажимать нечем), правки строки по `EDIT` — тоже.
- **Ожидание нажатия** — `MsgWaitForMultipleObjects` с выдержкой в четверть
  мига курсора: иначе курсор замирал бы, пока никто не трогает клавиатуру.
- **Аргументы командной строки берутся широкими** (`CommandLineToArgvW`),
  и путь с кириллицей до окна доходит — в отличие от хоста без окна.
  Файлы открываются через `host_common/fileio.*`, а не `fopen`.

Запись на дискету идёт в файл сразу (`host_common/disk_files.*`), а не при
выходе: программа на машине может уронить эмулятор, и терять из-за этого
записанный `SAVE DC` незачем. Образ, не открывшийся на запись, работает как
дискета с заклеенной прорезью — читается, но не пишется.

Полезно для оценки охвата:

```
iskra --tok ЛИСТИНГ [-b]      трансляция построчно; -b показывает байты
iskra --roundtrip ФАЙЛ        токены → текст → токены со сверкой байтов
iskra --run-file build/corpus/STAT04.bin 30 .05   запуск извлечённого файла
iskra --run-text corpus/hex/STAT04_text.txt 30 .05
iskra -i --run-file build/corpus/EDITOR.bin      пропуская ASMB и $GIO
iskra --console ОБРАЗ                             диалог с машиной
```

Прогнать разбор по всему корпусу и увидеть, на чём он встаёт:

```
for f in corpus/bin/* build/corpus/*.bin; do
    ./build/cmake/iskra.exe --run-file "$f" 1 1 1 2>&1 | grep '^разбор:'
done | sed 's/строка [0-9]*: //' | sort | uniq -c | sort -rn
```

На 2026-08-25 целиком разбирается **92 из 94** оттранслированных файлов и
**28 из 28** текстовых листингов. Остаток — не язык: `DIG_DEM` и `FS` дают
«длина строки выходит за поток», и дампы у них попросту обрезаны.

**Разбор и исполнение — разные вещи**, и цифра выше только про разбор:
программа может разобраться целиком и встать на первом же `PRINTUSING`.

## Что дальше

И разбор корпуса, и исполнение закончены: в `interp.cpp` сделано всё,
что транслируется. Дальше очередь не про язык, а про хосты.

### Сколько осталось

Цифры на 2026-08-26, считаны `py tools/probes/coverage.py` — **пересчитывать
им, а не править руками**. Проба сверяет ветки `Interp::exec()` с глаголами,
которые встречаются в корпусе.

```
исполняется 94 глагола, в корпусе встречается 93
не исполняется 3 глагола — 236 операторов из 32044 (0.7%)
целиком исполняются 47 программ из 72
потолок: 48 из 72 — остальным нужны ASMB либо $GIO
```

**Счёт «программ целиком» упёрся в потолок.** Из трёх оставшихся глаголов
два — `ASMB` и `$GIO` — здесь не появятся вовсе, а третий, `33`, встречается
на весь корпус один раз. Двадцать четыре программы из семидесяти двух без
эмуляции процессора до конца не доходят никогда, и мерить этой цифрой
дальнейшую работу нельзя.

**Цифра «целиком» вдобавок скошена составом корпуса** — это в основном
дисковые утилиты и редакторы, поэтому дисковые операторы и `ASMB` весят там
больше, чем весили бы в прикладных программах. Девять заходов подряд довели
долю неисполнимых операторов с 9.1% до 0.7%.

### Очередь работ

**Язык кончился.** Из 93 глаголов корпуса не исполняется три: `06 25 ASMB`,
`40 $GIO` и неопознанный `33`. Разобранных и невыполненных операторов не
осталось ни одного — очередь дальше не про язык.

1. **Клавиатура «Искры» в окне**: клавиши специальных функций (`DEFFN'` их
   разбирает, `KEYIN` разводит по строкам, а нажимать нечем), правка строки
   по `EDIT`, `STMT NUMBER`, `RESET`. Со стороны ядра всё готово:
   `Host::key_was_special()` есть, у оконного хоста он всегда false, потому
   что раскладку надо сперва найти в книге.
2. **Окна для остальных систем**: `src/host_x11/` (Xlib), `src/host_cocoa/`
   (AppKit, Objective-C++), `src/host_wasm/` (канва). Растеризатор и работа
   с образами уже общие, на каждую систему приходится 250–350 строк «завести
   окно, разобрать события, вывалить кадр». Проверять придётся в CI —
   с этой машины ни то, ни другое не запустить. У WASM своя загвоздка:
   блокирующий `wait_key` в браузере невозможен (`DECISIONS.md`, разд. 11).
3. **Мелочи**: кириллица в `argv` у хоста без окна (починка известна — брать
   широкие аргументы, как в `host_win32`), внятное сообщение о защищённой
   дискете.

**Отдельный разговор** (`docs/DECISIONS.md`, разд. 1):

- **`ASMB`** (`06 25`) и **`$GIO`** (`40`) — здесь их не будет вовсе: нужна
  эмуляция процессора 8080 с картой памяти и система команд БУВ, которой в
  книге нет. Ключ `-i` велит их пропускать, и тогда программа идёт дальше
  своими остальными операторами: у `EDITOR` `$GIO` стоит в строке 72, а с
  ключом прогон доходит до 5705.

### Графика сделана целиком

Исполняются все четырнадцать графических операторов: `06 0F ¤OPEN`,
`06 23 WINDOW`, `06 1D FRAME`, `06 19 NPLOT`, `06 15 DRAW`, `06 14 DDRAW`,
`06 13 DOT`, `06 1E LABEL`, `06 1F ¤COPY`, `06 1A ¤MOVE`, `06 1B TURN`,
`06 1C STRETCH`, `06 22 ¤LET` и `06 00 PLOT`. Растр — `core/raster.*`, сам
буфер — `core/gbuffer.*`, операторы — `core/interp_graphics.cpp`, решения —
`docs/DECISIONS.md`, разд. 15.

Устройство буфера разобрано целиком: заголовок в 43 байта, поток записей
`80`–`86`, живая картинка с образа сходится на 196 записях
(`docs/format.md`, разд. 5, «Заголовок и поток графического буфера»; проба —
`tools/probes/gbuffer.py`).

**`80`, `81` и `82` — это стёртые `84`, `85` и `86`**: бит `04` кода записи и
есть признак «рисовать», стирание элемента у `SLIDE` — это `AND(код,FB)`
(5240), восстановление `XOR(код,04)` (5290). Стёртая запись только двигает
текущую точку. Отсюда же следует, что **`¤COPY` чистит растр перед
выводом**: иначе стёртый элемент так и остался бы гореть.

**Три семейства операторов, три способа задать точку.** `NPLOT`, `DRAW` и
`DOT` берут координату; `DDRAW` — приращение от текущей точки (`SIG` 1560
рисует им прямоугольник); `PLOT` — тоже приращение, но кладёт точку не в
буфер, а прямо на устройство группы `PLOT`. Перья `PLOT` разобраны:
`U` вверх, `D` вниз, `R` сброс, `S` шаг знака, `C` размер знака
(`docs/format.md`, разд. 5).

**`¤MOVE`, `STRETCH` и `TURN` переписывают уже лежащие записи** одним
аффинным преобразованием, а новых не кладут. Смысл взят у подсказок `SLIDE`
5880–5930, точка у `STRETCH` и `TURN` неподвижна, единица угла — общая с
тригонометрией (`SLIDE` 260 ставит `SELECT D`). Выход за растр — **отказ
машины**: `SLIDE` ловит его через `ON ERROR` и печатает «ВЫХОД ЗА ЭКРАН».

**Что осталось неразобранным.** Байты `ORIGIN`, `DNPLOT` и `NDRAW` — эти
имена есть только в текстовых листингах, а все подкоды `06 xx` корпуса уже
названы. Код записи `83` в потоке — его не знает и сам `SLIDE` (ветка 1410
печатает «НЕИЗВ. ГЭ БАЙТ»). Байты заголовка буфера 7–39, и в их числе
40–43, куда `¤MOVE` с товарищами, судя по `SLIDE` 5890, кладут левый нижний
угол картинки: установить это нечем, и эмулятор их не трогает.

**Имена глаголов разобраны все, кроме одного.** Остался `33`. Операнд у него
разобран (номер строки парой BCD), а имя и смысл нет: вхождение на весь
корпус ровно одно, и текстовой копии той программы не существует
(`docs/format.md`, разд. 5).

## Допущения, ждущие проверки

Всё это работает, но подтверждения в книге не имеет. Если появится живая
машина или её ПЗУ — проверять в первую очередь.

- **Прокрутка** экрана при печати ниже 24-й строки.
- **Частота мигания курсора** — принято два раза в секунду. Сам вид курсора
  книгой описан (см. ниже), а мигал ли он и как быстро — нет.
- **`¤COPY` чистит растр перед выводом.** Прямо это нигде не сказано;
  выведено из того, что `SLIDE` после стирания элемента зовёт одну только
  «ВОССТ.ИНФ.» = `¤COPY /10` (1480), а стирание — это лишь сброс бита в коде
  записи (5240).
- **Управляющие коды устройства `10` взяты из руководства на 2282 Graphic
  CRT** (`docs/format.md`, разд. 5): `03` гасит поле, `0E` и `0F` — перо
  вверх и вниз, `0D` — размер знака. Рисует из них только двоичный вектор
  `E0`/`E6`, а его мы не принимаем: прямого вывода в обход буфера нет.
  `03` подтверждён независимо — своя таблица кодов даёт `03` = КТ, а
  `GRAFISN` 110 ставит гашение текста и графики подряд. **Три кода корпуса
  в таблицу 2282 не попадают вовсе** — `01`, пара `01 02` («ГАШЕН. МАР.»,
  `SLIDE` 1490) и `08 0B 09 06`, — значит БОСГИ повторяет ванга не
  полностью. Пакет с неизвестным кодом отвергается целиком; ключ `-i` велит
  такое пропускать. Из 43 операторов `PRINT /10` корпуса проходят 38.
- **Перевод строки, который `PRINT` дописывает сам, на устройство `10` не
  уходит**: у графического поля строк нет. Иначе `PRINT /10,HEX(03)` слал бы
  `03 0D 0A`. Явный `HEX(0D)` от дописанного при этом неразличим.
- **Наложение графики на знакоместа** — исключающее или. Книга о смешении
  символьного и графического устройств не говорит вовсе; сложение оставлено
  рядом (`Renderer::set_overlay`).
- **Цвета листа графопостроителя** — тёмное перо на светлой бумаге. Про них,
  как и про цвет люминофора, в книге нет ничего.
- **Лист графопостроителя** взят в тех же координатах, что и буфер, 560x256.
  Своих у него нет: книга называет устройство «планшетным» и больше о нём не
  говорит, разрешения не даёт, а размер картинки не задан ни в буфере, ни в
  его заголовке. `SLIDE` 7030, разговаривая с ним сам, спрашивает масштаб у
  человека и предлагает шесть (`docs/DECISIONS.md`, разд. 15).
- **Надпись рисуется тем же знакогенератором, что и текст**, глифом 5x8, и
  точка записи считается её левым нижним углом. Приращение в семь дискрет на
  знак сходится с шириной знакоместа, но своего набора у графической
  половины БОСГИ нам взять неоткуда.
- **Три байта признаков надписи.** В живой картинке они всюду `01 02 00`;
  первый принят за множитель размера — в тексте он пишется вплотную к имени
  буфера (`LABEL B¤()3,…`) и по умолчанию равен единице. Два других
  переносятся как есть, и что они значат, неизвестно. Множитель размера
  принят множителем и приращения (`7 × размер` на знак), и самого глифа.
- **Точка вне растра просто не рисуется.** Что делает машина, неизвестно;
  `SLIDE` ловит «ВЫХОД ЗА ЭКРАН» только у преобразований (5090), а не у
  вывода. Координата, не влезающая в два байта, — уже отказ: такую запись
  не построить.
- **Отображение `WINDOW`/`FRAME` держит интерпретатор**, а не буфер: в
  машине оно лежит в неразобранных байтах заголовка 7–39, и выдумывать их
  нельзя. Для корпуса неразличимо (`docs/DECISIONS.md`, разд. 15).
- **`¤OPEN` сбрасывает рамку буфера в тождественную.** Книга графики не
  описывает вовсе; принято по смыслу — буфер объявляется заново.
- **Операнды `¤MOVE`, `STRETCH` и `TURN` — в пользовательских единицах**, то
  есть проходят через `FRAME`, как координаты `NPLOT`. Сдвиг и точка — да,
  множители и угол — нет: они безразмерны. Книга графики не описывает, а в
  корпусе `SLIDE` задаёт рамку почти тождественной, и различить нечем.
- **Точка у `STRETCH` и `TURN` неподвижна.** Выведено из `SLIDE` 5950, где
  растяжение и обратное ему возвращают картинку на место; прямо это нигде
  не сказано.
- **Единица угла у `TURN` — та же, что у тригонометрии** (`SELECT D/G/R`),
  по умолчанию радиан. Довод косвенный: `SLIDE` 260 ставит `SELECT D`, а
  подсказка поворота (5930) просит градусы.
- **Байты заголовка буфера 40–43 эмулятор не трогает.** `SLIDE` 5890
  читает их перед `¤MOVE` и проверяет «их плюс сдвиг ≥ 0», то есть держит
  там что-то вроде левого нижнего угла картинки; кто их заполняет и по
  какому правилу, не установлено.
- **`¤LET <буфер>=<буфер>` копирует картинку, `=0` опустошает буфер.** В
  корпусе первая форма встречается только присваиванием самому себе, и там
  наблюдаемого действия нет вовсе — но строка `EDITOR` 1236 существует
  ровно ради этого оператора, значит побочное действие у него есть. Скорее
  всего это те же байты 40–43 (см. выше).
- **Приращение надписи при преобразовании достаётся линейной части.** В
  записи `86` лежит смещение, а не координата, поэтому переносу оно не
  подлежит; поворот и растяжение его достают. Само приращение считается
  числом со знаком — иначе повёрнутая надпись была бы непредставима, — а
  две координаты в нём порознь; `SLIDE` 1430 складывает все четыре байта
  одним `ADD C`, и заём из Y у него ушёл бы в X. Книга молчит.
- **Перо `R` у `PLOT` ставит перо в начало координат** и возвращает размер
  и шаг знака к умолчанию. В корпусе `PLOT <,,R>` стоит в начале каждой
  серии (`SLIDE` 5650, 6160), а следующая группа задаёт первую точку —
  значит отсчёт после него ведётся от нуля.
- **Шаг знака у `PLOT` до первого `S` — семь дискрет**, как у `LABEL`.
  Другого числа взять неоткуда, а без шага надпись легла бы в одну точку.
- **Цвет люминофора** не установлен вовсе: в руководстве его нет, по
  чёрно-белым снимкам не разобрать. Взят зелёный (`30 D8 30` на чёрном) —
  обычный для трубок тех лет, но это догадка по времени и месту, а не
  прочитанное. Меняется хостом через `Renderer::set_colors`.
- **Знакоместо 7x10.** Глиф 5x8 и восемь строк на знак прочитаны прямо с
  рис. 3.1, а поле вокруг него — нет: принято 7x10, два столбца просвета
  справа, снизу межстрочный интервал и строка курсора. Семёрка не выдумана:
  приращение точки у надписи графического буфера — ровно семь дискрет на
  знак, и 80 знакомест дают 560, то есть ширину растра (`docs/format.md`,
  разд. 5). А вот **как поделены эти семь точек** — глиф слева, просвет
  справа, — прочитать неоткуда: сама «Искра» рисует символы аппаратным
  знакогенератором, и как у неё расположен текстовый блок на растре, книга
  не говорит. Высота 10 остаётся догадкой: 24 строки дают 240, и до 256
  недостаёт ровно двух полей по 8 точек.
- **Точка квадратная** (`DOT_TALL` = 1). Отношение сторон трубки книгой не
  описано, а `SLIDE` 190 спрашивает «ОТНОШЕНИЕ ДЛИН ДИСКРЕТ X/Y» и
  предлагает по умолчанию единицу. При растре 560x256 кадр выходит 2.19:1.
- **Ширины столбцов в выдаче `LIST DC`.** Ширины полей из данных сомнений не
  вызывают (имя — восемь байт, номер сектора — пять цифр), а вот пробелы
  между ними взяты так, чтобы заголовки стояли над своими полями: в скане
  книги три примера, и в каждом разбивка своя.
- **Пороги экспоненциальной записи**: принято «плотно при порядке от −12
  до 12».
- **Мантисса E-формата — восемь знаков после точки.** Основание — один
  пример в разд. 13.6.
- **Условие цикла проверяется в `NEXT`**, а не при входе в `FOR`.
- **`TAB(` двигает курсор только вправо**; что делает при позиции левее
  текущей — неизвестно.
- **`CONVERT` без образа** прижимает число вправо к длине приёмника.
  Книга такой формы не описывает вовсе.
- **`PRINTUSING`, когда элементы кончились раньше описаний формата.** Все
  примеры главы 16 сходятся ровно; принято, что остаток образа печатается
  как есть, и незаполненные разряды видны знаками `#` — так же, как при
  переполнении. Обратный вариант («печать обрывается») книга не исключает.
- **Символьное значение короче поля** дополняется пробелами справа. Книга
  описывает только обратный случай — что лишнее не печатается.
- **Устройством вывода `PRINTUSING` считается экран при адресе `05`, всё
  прочее уходит на АЦПУ.** Из таблицы ФАУ известны только `05` (дисплей) и
  `0C` (АЦПУ); что делать с остальными адресами, не сказано.
- **Точка без дробных разрядов** (`%######.`) печатается. Прямо это в книге
  не сказано, но сказано, что точка «воспроизводится при печати».
- **`DATA SAVE BT` и `DATA LOAD BT` без приставки** кодируются как есть, без
  байтов приставки: устройство берётся из группы `TAPE` (разд. 11.5). В тексте
  форма встречается 81 раз (`SLIDE` 7280, `ДЕМ8` 230, `AN-DEM2` 1450), а в
  токенах — ни разу: там во всех 793 операторах стоит `DC` либо `DB`. Довод
  тот же, что у `RESTORE` без номера строки: чего нет в тексте, того нет и в
  потоке; машина могла бы вместо этого писать адрес из таблицы устройств.
- **Формы `RESTORE` без номера строки** — голая и с одним выражением. Книга
  их описывает (разд. 4.9), `SLIDE` 230 пользуется голой, но в токенах их в
  корпусе нет ни разу. Принято, что операндов тогда просто меньше: запятая —
  тот же `DE`, чего нет в тексте, того нет и в потоке. Машина могла бы вместо
  этого всегда писать `DE 00 00`.
- **`RUN <номер>` сохраняет указатель начала считывания**, как сохраняет и
  значения переменных (разд. 4.1). `RUN` без номера и `CLEAR` его сбрасывают.
  Про указатель книга не говорит вовсе — принято по сходству с переменными.
- **`RESTORE <N>,<строка>` при нехватке значений в этой строке** переходит в
  следующий оператор `DATA`, а не останавливается на конце. Книга такого
  случая не разбирает; в корпусе `N` всегда в пределах строки.
- **Приёмник адреса в скобках у `BA`/`DA`/`DC` и `END` у `DA`.** Книга обе
  формы описывает (разд. 18.9.1, пример 18.29 `DATA SAVE DA F(P,P) END`), но
  в токенах их в корпусе нет. Принято: запятая — тот же `DE`, что везде,
  признак конца — тот же `D7`, что у `DATA SAVE DC END`.
- **`DATA SAVE DC END` не двигает текущий сектор.** Прямо это не сказано, но
  сказано, что концевая запись «определяет сектор, откуда можно записывать
  данные» (разд. 18.4) — то есть следующая запись должна лечь на её место.
- **`DATA LOAD BA` в поле длиннее сектора** дополняет остаток пробелами, как
  обычное присваивание символьной переменной. Книга описывает дополнение
  нулями только для записи (`DATA SAVE BA`), про чтение молчит.
- **`HEXPRINT` числа** печатает его восьмибайтовым дисковым представлением.
  Книга описывает `HEXPRINT` только для символьных значений; что машина
  делает с числом, там не сказано вовсе.
- **Хвостовая точка с запятой у `HEXPRINT`** подавляет перевод строки, как
  у `PRINT`. Книга говорит только про разделение элементов внутри оператора.
- **Какая из двух строк `KEYIN` для обычной клавиши, а какая для клавиши
  спецфункций.** Принята вангова раскладка (первая — обычная, вторая —
  спецфункция); корпус её подтверждает косвенно, разбор в `docs/format.md`,
  разд. 10.
- **Имя переменной вида `A0` в адресе устройства** круга «токены → текст →
  токены» не переживёт: ровно две шестнадцатеричные цифры после `/`
  разбираются обратно как литерал. У машины та же неоднозначность в её
  собственном листинге (`docs/format.md`, разд. 10).
- **`DATA LOAD BT` в поле короче принятого блока** берёт столько байт,
  сколько в поле помещается. Книга операторов `BT` не описывает вовсе.
- **Маска `hh` у `$TRAN(`.** Книга её описывает, но в корпусе её нет, и
  байтов у неё неизвестно: хвост `DE 00` после скобки принят за признак `R`.
  Без маски табличная форма оставляет байт как есть, если код больше длины
  таблицы, — так книга и говорит для случая незаданной маски.
- **Выросшее сверх поля у `REPLACE` обрезается.** Книга говорит только про
  обратный случай — что короткое дополняется пробелами.
- **Ширина номера строки в символьном буфере.** Записывается как в
  листинге, без дополнения нулями. В корпусе эта форма встречается только с
  четырёхзначными номерами, и отличить «ровно четыре» от «сколько есть»
  нечем (`docs/format.md`, разд. 10).
- **`SAVE` в буфер добивает остаток пробелами.** `EDITOR` 5195 чистит буфер
  сам перед сохранением, так что различить нечем.
- **Какой из кодов `CLEAR` — `V`, а какой `N`.** Принято `11` = `V`,
  `12` = `N`; в корпусе оба встречаются только там, где разницы нет.
- **`RETURN CLEAR ALL` стирает список адресов возврата целиком.** Книга
  описывает только форму без `ALL` («список уменьшается на один адрес»),
  а байт `CB` берётся из корпуса.
- **`CLEAR P`, стерший собственную строку, останавливает программу.** Что
  делает машина, книга не говорит: она эту форму разбирает только в диалоге.
- **Тетрада знака и байт порядка в упаковке.** `0` плюс, `1` минус, порядок
  байтом со знаком — по образцу восьмибайтового числа. Цифровая часть
  упаковки подтверждена живыми данными, а эти две вещи в корпусе не
  встречаются ни разу (`docs/format.md`, разд. 10).
- **Знак стоит первой тетрадой**, разряды за ним в порядке образа, а
  незанятая последняя тетрада — нуль. Книга говорит только, что знак
  «упаковывается в половину байта».
- **Хвост более длинного приёмника** у `AND`/`OR`/`XOR`/`BOOL` со второй
  переменной остаётся нетронутым. Книга про разные длины у логических
  операторов молчит вовсе (у `ADD` — оговаривает выравнивание по правому
  краю, и оно сделано).
- **`MAT <массив>=ZER` над символьным массивом** — отказ, а не заполнение
  поля. Что машина делает с `ZER` у строк, неизвестно, а в корпусе такой
  формы нет.
- **Устройство `DATA SAVE DC CLOSE` не сбрасывает** — обнуляются только три
  адреса строки. «Записывая нули во все графы таблицы устройств» можно понять
  и как «включая адрес устройства», но тогда `SELECT` пришлось бы повторять
  после каждого закрытия файла.
- **`NUM`**: пробел между знаком и цифрами допускается, хвост из одних
  пробелов входит в длину. Сходится со всеми тремя примерами книги, но
  выведено из них, а не прочитано.
- Поле символьной переменной **растёт по требованию**, если обращение
  выходит за описанные размеры: по таблицам «строка-скаляр или массив
  строк» не различаются.
- **Фактические параметры `GOSUB'` вычисляются все до первого
  присваивания.** Формальный параметр — обычная глобальная переменная, и
  корпус зовёт подпрограммы через их же параметры (`EDITOR` 6855:
  `GOSUB '100(L3,A%,1)` при `DEFFN '100(L1,L4,L3)`), но там порядок ничего
  не меняет — различающего примера нет ни в книге, ни в корпусе.
- **При повторе имени подпрограммы побеждает первое `DEFFN'`.** Книга
  говорит только, что машина ищет просмотром текста программы. То же принято
  и для функций пользователя при повторе имени в `DEFFN`.
- **Формальная переменная `DEFFN` — обычная глобальная переменная**, и
  прежнее значение после обращения не восстанавливается. Своего места для
  неё в машине нет: в потоке это обычный индекс переменной, такой же, как у
  формальных параметров `DEFFN'`. Книга об этом не говорит вовсе.
- **Глубина вложенности обращений `FN` ограничена тридцатью двумя.**
  «В качестве новых функций могут использоваться … другие функции,
  определённые в данной программе» (разд. 4.8), а вот что машина делает с
  функцией, зовущей саму себя, книга не описывает. Без ограничения
  `DEFFN Q(X)=FNQ(X)` обвалил бы стек молча.
- **Буква устройства у `COPY` необязательна, и это неоднозначно.** Байт
  `00`/`01`/`02` в начале операндов дискового оператора — либо буква
  `F`/`R`/`T`, либо индекс переменной 0…2; принято «≤ 2 — буква», как и во
  всех прочих дисковых глаголах. У `COPY` это заметнее: границы начинаются
  сразу за приставкой, и `COPY (A,B) TO R` при малом индексе `A` разберётся
  не так. В корпусе такой формы нет (`docs/format.md`, разд. 5).
- **Таблицы переменных при частичной загрузке сегмента** берутся у сегмента,
  но область не усекается: записи с индексами больше, чем у него, остаются от
  прежней программы. Строки, которых не стирали, продолжают на них ссылаться.
  Как это устроено в машине, книга не описывает вовсе.
- **`COPY` без адреса приёмника** кладёт каждый сектор на его собственное
  место. Книга разбирает только форму с адресом (`TO R(50)`), а про голую
  говорит лишь «копируется весь диск полностью».
- **`COPY` в пределах одного дисковода с наложением областей** копирует с
  конца, чтобы хвост источника не затёрся раньше, чем его прочитают. Книга
  говорит «на другой диск» и такого случая не разбирает вовсе.
- **Отказы `COPY`** (границы наоборот, за концом диска, не вмещается) —
  ошибки машины, но кодов у них мы не знаем, и `ON ERROR` получает `??`.
  Что это именно ошибки машины, видно из `LКОПИДИС` 1240: там `ON ERROR`
  стоит прямо перед `COPY`, а строкой позже снимается.
- **`LIST <номер>` без запятой** выдаёт текст с этой строки и до конца —
  так же, как `LIST <номер>,`. Книга описывает только форму с запятой.
- **Ошибки диалог показывает своими словами**, а не как `^ERR 06` с
  указателем на место ошибки (разд. 3.3). Код машины печатается отдельной
  строкой `ERR nn`, когда он есть; у ограничения эмулятора кода нет.

## Известные шероховатости

- **Знаков `` ` ``, `{`, `|`, `}`, `~` у машины нет.** В КОИ-7 Н2 по этим
  кодам стоят Ю, Ш, Э, Щ, Ч, и `PRINT "|"` высветит Э. Это не изъян
  эмулятора, а состав знакогенератора; но тексты, набранные с оглядкой на
  ASCII, выглядят неожиданно. По той же причине подчёркивание высвечивается
  как Ъ.
- **Строчные буквы приводятся к прописным** и на клавиатуре, и на выходе к
  экрану: строчных глифов у машины нет ни одной. Набранное `10 print "abc"`
  ложится в текст программы как `10 PRINT "ABC"`.
- **`^` расходится с книгой в последнем разряде.** Пример 4.20 печатает
  `2.924017738212` и `3.530348335325`, а у нас выходит `…213` и `…326`.
  Точные значения — 2.92401773821286… и 3.53034833532606…, так что книжные
  цифры не выходят ни округлением, ни усечением: степень считается через
  логарифм и показательную функцию, и накопленная ошибка у машины своя.
  Третье значение примера (целое `2`) сходится точно.
- Кириллица в аргументах командной строки не доходит **до хоста без окна**
  (`iskra --cat ОБРАЗ СТЬЮД` не находит файл). Расходятся кодировки `argv`
  и каталога; с латинскими именами всё работает. У `iskra-win` этого нет:
  он берёт аргументы широкими и открывает файлы через
  `host_common/fileio.*`. Тем же способом чинится и `main.cpp` хоста без
  окна, руки не дошли.
- `NUM`, `LEN`, `VAL`, `POS` в текстовой записи требуют скобок, в
  токенизированной их нет вовсе — разбор терпит оба варианта.
- Диалог в терминале (`--console`) повторяет экран построчно: чего терминал
  стереть не может, то остаётся. После `CLEAR` он отбивает пустую строку и
  печатает всё заново. Правки строки клавишей `EDIT` нет — только забой.
- Кириллица со стандартного ввода в терминале Windows приходит не в UTF-8,
  и имена файлов кириллицей набрать в диалоге не получится. Та же беда,
  что с `argv`.
- Дискета, защищённая ключом `--rN`, при попытке записи даёт «не пишется
  сектор», а не «дискета защищена»: `Host::disk_write` возвращает голый
  `false`, и слой каталога причины не знает. Внятнее было бы спрашивать
  защиту у хоста, но это расширение `host.h` ради удобства сообщения.
- Из Бейсика подключить образ нельзя — только ключами при запуске. Файлового
  диалога в окне нет.
- **`DATA` с именем символьной переменной не работает** — ни трансляция, ни
  `LIST`. Книга такую форму допускает (`DATA 1986,E,M¤,"ОТЧЕТ"`, разд. 4.9),
  но упирается она в тот же открытый вопрос формата: «скаляр или массив» у
  символьной переменной по таблицам не различается, `build_vars` угадывает
  «массив», и байты следующего значения читаются как список индексов. С
  числовыми переменными в `DATA` всё работает — у них признак массива в
  таблицах есть. В 28 листингах корпуса эта форма не встречается ни разу.
- **Числовая константа с отрицательным порядком не транслируется**:
  `A=2.3E-9` даёт «отрицательный порядок ещё не кодируется». Положительный
  разобран (`1E6` = `E6 11 10 06`, `STAT08` 480), а отрицательного в корпусе
  нет ни разу, и байт знака выдумывать нельзя — тот же случай, что `XOR` и
  `SELECT D/G/R`. Обходится делением.
- У АЦПУ нет ширины строки: `SELECT PRINT 0C(130)` ширину запоминает
  (её видно в `LIST%`), но перенос по ней не делается — лента складывается
  из того, что напечатали, а переводы строк ставит сама программа.

## Что уже известно про машину

- Экран: **80 позиций x 24 строки**, атрибуты только позитив и негатив.
- **Обычное состояние экрана — «негативное»: светлые знаки на тёмном поле**
  (разд. 2.1 и 17.1). «Позитивное» — тёмные знаки на светлом — это выделение
  поля, а не норма. Названия легко перепутать, и **книга сама их путает**:
  приложение 1 приписывает их кодам наоборот. Разбор противоречия —
  `docs/format.md`, разд. 10, «Противоречия в самой книге». В коде
  `ATTR_NEGATIVE` = 0 и есть значение по умолчанию.
- **Курсор — подстрочная черта**, а не заливка знакоместа: «место, на котором
  высветится очередной символ, автоматически указывается с помощью курсора
  (подстрочной черты)» (разд. 2.1). Разд. 3.5 говорит то же косвенно —
  курсор «подводят под» символ, а `DELETE` стирает символ «над курсором».
  То же и у Wang: в его знакоместе 10x11 курсор занимает нижнюю строку во
  всю ширину, под глифом 8x8, который сидит со смещением (1, 2).
- `AT(строка, позиция [, сколько_стереть])` — отсчёт с единицы; третий
  аргумент стирает вправо от курсора, курсор остаётся на месте.
- Коды управления дисплеем: `01` НЗ, `03` КТ, `07` ЗВ, `08` ВШ, `09` ГТ,
  `0A` ПС, `0C` ПФ, `0D` ВК, `11` СУ1 (негатив), `12` СУ2 (позитив). Код
  для **НС** («в первую позицию следующей строки») в таблице книги не найден.
- **Дисплей — два устройства, а не одно.** Таблица ФАУ (приложение 1)
  перечисляет `05` «блок отображения символьной информации» и `10` «блок
  отображения графической информации» порознь; трубка при этом одна, и в
  заводской документации она зовётся БОСГИ — «блок отображения
  символьно-графической информации» (сноска на с. 6). Символы рисует
  аппаратный знакогенератор: они «фиксированного размера в фиксированных
  позициях экрана» (разд. 1.2), а не программой по точкам.
- **Графика — 560x256.** Книга графических операторов не описывает вовсе,
  растр выведен из корпуса. По вертикали 0…255: `NPLOT B6¤(),0,245`,
  `NPLOT B¤(),215,248`, `WINDOW 0,…,0,255`. По горизонтали 0…559, и доводов
  три: `SLIDE` 170 предлагает границей экрана 559 и свой буфер выкладывает
  на `/10` (трубка), `SIG` 7320 задаёт `WINDOW 0,559,0,255` и строкой ниже
  рисует `NPLOT B¤(),550,50` — в 512 это не влезло бы, — а приращение
  надписи в живой картинке с образа равно 7 дискретам на знак, то есть 80
  знакомест строки дают ровно 560. Разбор — `docs/format.md`, разд. 5,
  «Растр графики». Это именно экран: `SELECT PLOT` по умолчанию `10`, а не
  `14` (графопостроитель). Этот же растр служит кадром и в символьном
  режиме: 80x24 знакомест по 7x10 дают 560x240 и занимают его по ширине
  целиком, оставляя поля по 8 точек сверху и снизу.
- **Знакогенератор снят с руководства по БОСГИ** — рис. 3.1 «Номенклатура
  символов» (`docs/BOSGI-FONT-fix.jpg`, разбор — `tools/probes/bosgi_font.py`,
  результат — `src/font/koi7-5x8.txt`). Это уже не чужой шрифт: глифы самой
  «Искры», 96 знаков **5x7 в поле 5x8** (верхняя строка знакоместа пуста у
  всех). Подробности — `docs/format.md`, разд. 11.
- **Экран семибитный, кодировка КОИ-7 Н2**, коды `20`–`7F`. Два отличия от
  стандартной таблицы: `5F` — не подчёркивание, а **Ъ**, а `7F` **пуст**
  (Ъ оттуда и переехал на `5F`). Строчных букв нет ни одной — ни латинских,
  ни кириллических.
- В позиции `24` машина высвечивает **¤**, а не доллар. На рис. 3.1 так и
  есть, подменять нечего.
- **Внутри эмулятора текст в КОИ-8, и бит сбрасывается на выходе к экрану**
  (`Screen::put` → `koi8_to_koi7`), а не на входе с клавиатуры: у машины
  старший бит не возникает вовсе, а у нас семибитный код кириллической
  буквы в КОИ-8 занят латинской. Клавиатура только приводит к прописным
  (`koi8_upper`). Разбор — `docs/format.md`, разд. 11, «Граница с КОИ-8».

## Диски

Образы дискет лежат вне репозитория:
`DSKCommander/docs/samples/Iskra226/345_dk_spb/`.

**Автоопределению типа диска верить нельзя:** 8-дюймовые образы «Искры» не
отличаются по геометрии от CP/M GMD-7012, и `detect_fdd_type()` выбирает
CP/M — каталог читается как мусор. Поэтому `DiskImage::open()` берёт из
автоопределения только формат файла (`format_only = true`), а тип диска и
файловую систему навязывает всегда. Других дисков у эмулятора не бывает.

Все 42 образа — по 256256 байт (1001 сектор по 256). Каталог есть у 32,
у 10 его нет, и это не повреждение: 4 загрузочных с самим интерпретатором
(сигнатура `06 90 09 90 07 90`, дальше 18 знаков — «BASIC 02» или
«BASIC PL5» с датой), 2 пакета `~АСМБ`, 2 диска абсолютной адресации без
указателя, 2 пустых. Разбор и признаки — `docs/format.md`, разд. 2.

```
py tools/probes/disk.py kind ОБРАЗ        вид диска
py tools/probes/disk.py list ОБРАЗ        каталог
py tools/probes/disk.py data ОБРАЗ ИМЯ    файл данных записями и значениями
py tools/probes/dataprobe.py              перепись файлов данных по всем образам
py tools/probes/gbuffer.py                поиск картинок: поток графического буфера
py tools/probes/hash.py [ИМЯ LS]          хеш имени в сектор указателя
```

Хеш имени файла разобран (`docs/format.md`, разд. 2) — это «старый» хеш
Wang 2200, сходится на всех 303 записях каталога. Он вырождается, когда
число секторов указателя кратно трём, поэтому при создании образов
`LS` кратным трём брать нельзя.

Формат записей данных и 8-байтовых чисел разобран по образам целиком
(`docs/format.md`, разд. 2). Тип «данные» в каталоге ничего не говорит
о внутреннем устройстве файла: из 65 таких файлов только 37 записаны
операторами `DATA SAVE DC`/`DA`, остальные — сырые блоки от `DATA SAVE BA`.

## Корпус

**Сверх корпуса есть 49 образов дискет** (`DSKCommander/docs/samples/Iskra226`
и вложенные). Их перепись сделана `tools/probes/` и разложена в `build/dsk/`:
227 программных файлов, 198 различных по содержимому — 124 оттранслированных,
73 текстовых. Из них 105 в корпус не входят. Пары «текст + токены» ищутся по
совпадению строковых литералов, а не по именам: номера строк круглые у всех
и ничего не различают.

**Найденная пара `SLIDE` ↔ `SL2`** — первая с графикой; ею разобраны подкоды
`06 1A`, `06 1B`, `06 1D` и поправлен `06 1C` (`docs/format.md`, разд. 5).
Тригонометрия по-прежнему без пары: `SIG`, `FAN01`, `AN-DEM2` и `DL.1EX`
оттранслированных двойников не имеют.

- `corpus/hex/` — 79 hex-дампов: `*_bin.txt` токенизированные, `*_text.txt`
  текстовые листинги. 12 пар «одна программа в обоих видах».
- `corpus/bin/` — 43 двоичных файла без текстовых пар.

**Осторожно с парами:** у `M1`, `STAT00`, `STAT05`, `STAT001`, `STAT01`
текстовая и двоичная копии — разные редакции программы. Для сверки годятся
`EDITOR`, `VICT`, `STAT02`, `STAT03`, `STAT04`, `STAT08`, `STAT09`.

## Правила работы

- Гипотезы о формате проверять на всём корпусе, а не на одном файле. В
  `docs/format.md` есть примеры того, как правдоподобная догадка разваливалась
  на втором файле.
- Найденное — записывать в `docs/format.md` с указанием, чем доказано
  (файл, строка, байты). Отрицательные результаты тоже.
- `docs/ARTICLE-wiki.txt` — статья для emuverse; таблицы токенов там должны
  быть отсортированы по возрастанию токена.
- Скан книги (`docs/book/*.pdf`) и сканы страниц (`docs/*.jpg`) в git не
  попадают — они в `.gitignore`.
